# Reference Cogit Agent

A cloneable resident-agent repository that exercises the real Cogit SDK and
runtime contracts: typed actions, tool exposure, approval parking, manifest
pipelines, durable cases, queue workers, migrations, evals, and containers.
The domain is intentionally synthetic so the repository can be copied without
bringing product-specific code with it.

## Validate the agent

Prerequisites: Python 3.11+, [uv](https://docs.astral.sh/uv/), and optionally
Docker.

Install the verified framework cohort:

```powershell
python scripts/verify_framework_wheels.py
uv lock --check
uv sync --all-extras --frozen --no-editable
```

Run the full local gate:

```powershell
.\scripts\check.ps1
```

```bash
bash scripts/check.sh
```

That command validates the manifest and action parity, runs static checks and
tests, starts the real HTTP server, and executes `cogit-runtime eval`.

## Framework dependencies

Template 0.1.25 selects SDK 0.5.16, Runtime 0.3.31, AgentDB client 0.2.13,
and tool-core 0.1.3. The optional workspace profile retains shell and browser
0.1.2 for UTF-8 PowerShell handling and confirmed owned-browser cleanup.
Provider profiles pin the universal-policy module alongside
the existing Runtime policy module. This adds code and package configuration;
business prompts and classifier criteria are unchanged. No live invoice policy
is published or activated by installing this cohort.

The `apply_resolution` action requires `records.write`, an idempotency key
and approval. Its fenced AgentDb command commits the resolution and request-key
binding together. The `lookup_resolution` action requires `records.read` and
reads the committed result through a fenced query. Both use the tenant and
installation supplied by AgentDb. These are code, contract, dependency and
test changes. The optional workspace prompt drops the retired memory-tool
instructions.

Bootstrap preserves the unchanged formatting and lint gate for package names
through the supported 48-character limit, including longer default agent IDs.
Tests derive display names from the selected manifest and use stable import/path
layouts. No formatter must be installed before bootstrap, and no post-init
formatting repair is required.

The candidate targets physical AgentDB head 216 and retains public wire schema 211. Its universal-policy module interface
has an operational capacity of 1,000 cumulative requirements;
the HTTP and SDK contracts allow up to 1,024. A larger set fails closed through
the module interface. Upstream bootstrap fixes and manifest-selected entrypoint
validation are retained. The default agent pins immutable
module 1.1.7 for physical head 216 and preserves the exact 1.1.6 and 1.1.5 bundles.
Committed producer revisions and exact selected wheel hashes are recorded in
`vendor/wheels/PROVENANCE.md` and `vendor/wheels/cohort.json`.

The framework packages come from the exact vendored wheels recorded in
[the cohort provenance](vendor/wheels/PROVENANCE.md), without sibling source
checkouts or private build credentials. This cohort is approved for installation preparation only. Local Windows/Linux installation and image
dependency checks are preparation evidence; final cohort, hosted checks and
canonical queue execution require their separate acceptance gates.

The default `cogit.yaml` runs one worker claim at a time, matching the
canonical AgentDb worker admission rule. The optional database manifest
generated by `scripts/enable_database.py` uses the same concurrency. Canonical
workers additionally need the exact agent/framework/provider artifact cohort and a receipt
bound to published route IDs; the [database example](docs/database-example.md#prepare-and-bind-the-canonical-worker-cohort)
shows preparation and startup.

`cogit.yaml` is the authored agent definition. Its `metadata.entrypoint` selects
the installed Python class, including after bootstrap; the worker command uses that declaration. The generated database profile selects its
own class in the same field. Cohort preparation rejects a conflicting explicit
selector or a class absent from the agent wheel. `executable.json`, `prepared.json`
and the published receipt are generated commitments, not another agent manifest.
The template build guard expects a concrete top-level class in the selected `.py`
module or package `__init__.py`; re-export aliases are outside this template
convention. This does not restrict Runtime's general Python import support.
The compatibility `main.py` ASGI factory still supplies its Python class through
the programmatic Runtime API. The CLI and canonical worker use YAML selection.

Manifest validation and action-contract export also use that selected class.
After changing the entrypoint or its bindings, regenerate the derived contract
with `python scripts/export_action_contract.py`, then run
`python scripts/validate_manifest.py`. Validation is read-only and rejects a
stale action contract, including when selecting the database profile in `cogit.yaml`.

The default gate checks lock freshness before frozen installation and runs
behavior tests against installed packages with the source import path disabled.
Bootstrap and packaging tests still inspect repository files. The build backend
is pinned separately with its constraints and archive receipt in
`vendor/build-toolchain.json`; the runtime lock alone does not freeze build tools.

For explicit framework development, first install the frozen environment above,
then install checkouts whose package versions satisfy the exact metadata pins:

```powershell
uv pip install --no-sources -e ../agent-db/clients/python-canonical `
  -e ../cogit-agent-sdk -e ../cogit-runtime -e ".[dev]"
.\scripts\check.ps1 -SkipSync -SkipImage
```

```bash
uv pip install --no-sources -e ../agent-db/clients/python-canonical \
  -e ../cogit-agent-sdk -e ../cogit-runtime -e '.[dev]'
bash scripts/check.sh --skip-sync --skip-image
```

This source-based check is development evidence. It does not validate the
vendored cohort. Change framework versions only with a reviewed cohort refresh.

## Optional general workspace tools

The template can select installed typed filesystem, process, shell and
Playwright providers without changing its agent class. The workspace profile
adds a general problem-solving prompt; AgentDB owns policies and Runtime
enforces them. Dedicated browser sessions and agent-written Playwright scripts
share an explicitly owned login. Read [the standalone setup and boundaries](docs/dynamic-tools.md).

### Optional Responses model

A deployment that needs a model can select `runtime.model.profile: sdk` and
declare its OpenAI model with `openai_api: responses`. Install the workspace
extra for the provider and set `OPENAI_API_KEY` in the worker environment.
Publish the updated descriptor and cohort with the appropriate AgentDb model
policy, bounds, and spend authority before admitting model work. The
[dynamic tools guide](docs/dynamic-tools.md) describes that preparation.

## Prepare and run the AgentDb worker

The default `cogit.yaml` pins the AgentDb module and a deterministic queue
pipeline. Build the project wheel and prepare the exact deployment cohort:

```sh
uv sync --frozen --no-editable
uv build --wheel --out-dir .data/agent-wheel
uv run --no-sync python -I scripts/worker_cohort.py prepare --manifest cogit.yaml --agent-wheel-dir .data/agent-wheel --output .data/worker-cohort
```

Install the approved module bundle, publish the prepared cohort, and bind its
receipt to the published installation and worker pool. Follow the
[AgentDb deployment example](docs/database-example.md) with the root
`cogit.yaml`. Set the worker environment variables shown in `.env.example`
from that deployment, then start the installed worker:

```sh
cogit work --project . --environment
```

The Runtime CLI can also start the worker using
`uv run --no-sync python -I -m cogit_runtime work --manifest cogit.yaml`.
Both commands select the authored root manifest. The example requires no
model provider credential.

Submit a request with the authorized AgentDb member client in
`examples/durable_run.py`. The queue pipeline writes and reads the request
through its pinned exports, then publishes the result artifact through
AgentDb. The worker token is for admitted work. The member token admits
requests and reads the resulting lifecycle and artifacts.

Existing local resolution data remains in place. Migrating it requires an
explicit mapping from each former tenant and organization to the authorized
AgentDb tenant and installation, followed by a verified import.

## Run with Docker

Build the worker image with `scripts/build_image.ps1` on Windows or
`bash scripts/build_image.sh` on Linux. Prepare and publish the cohort
extracted from `/app/worker-cohort` in that image. Configure its published
receipt and worker settings, then run `docker compose up`. Compose starts
the worker against the configured AgentDb service and mounts the receipt
read-only. See the [operations guide](docs/operations.md).

## Repository contract

- `cogit.yaml` is the declarative source for actions, pipelines, model, and
  runtime defaults.
- `src/seller_agent/agent.py` contains SDK lifecycle and action adapters.
- `src/seller_agent/domain.py` and `schemas.py` contain runtime-free domain
  code.
- `main.py` is the only ASGI composition root.
- `evals/` contains data-only black-box suites; it never imports agent code.
- AgentDb owns durable execution state, queue coordination, and the
  module's business records. Runtime executes the worker pipeline.

When adding an action, update both the decorator and `cogit.yaml`. The validation
script rejects drift. Expose read-safe actions as tools; keep approval-gated
writes out of the model tool surface unless the policy intentionally allows
them.

See `docs/architecture.md` for ownership boundaries and
`docs/operations.md` for deployment and recovery guidance.

## Optional reduced database descriptor

`scripts/enable_database.py` generates a descriptor that exposes only the
deterministic request action. Publish a separate cohort and receipt for that
explicit descriptor. The default deployment uses the root `cogit.yaml`.
